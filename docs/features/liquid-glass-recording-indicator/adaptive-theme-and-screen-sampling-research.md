## 1. 背景与用户诉求

在 Type4Me 引入 macOS 原生液态玻璃（Liquid Glass）录音指示条后，浮动条窗口（`FloatingBarPanel`）采用了无边框、完全穿透的非激活窗口架构。原生玻璃材质能够自然地折射桌面壁纸及底层第三方窗口的内容。

随之产生了一个自然的产品设想——**「自适应（Auto / Adaptive）」外观模式**：
- 用户期望指示条能够智能感知当前所处屏幕区域的背景明暗程度；
- 在浅色背景（如浅色壁纸、Safari 白色网页）下，玻璃呈现透光浅色，文字与按钮自动转为高对比度深色；
- 在深色背景（如暗色壁纸、VS Code、终端）下，玻璃呈现深邃暗色，文字与按钮自动转为高对比度银白色；
- 避免人为加垫底色（如 `glassDarkContrastFloor`），实现纯粹的原生折射与视觉自适应。

## 2. 为什么 macOS 无法“天然感知”底层窗口的明暗？

许多开发者直觉上认为：既然 `NSVisualEffectView` 或 macOS 26 的 `.glassEffect()` 能够根据背后内容自动折射变色，那么上层的文字和按钮也应当能自动读取同一份背景亮度。但现有公开的常规 AppKit / SwiftUI 材质 API **没有提供零额外屏幕采集权限的“读取合成后背景像素”接口**；若要按真实底层像素计算亮度，需要进入屏幕捕获类 API 的权限与性能边界。

### 2.1 WindowServer 合成层与应用沙箱的安全隔离
- **GPU 混合合成发生在客户端之外**：
  macOS 窗口系统（WindowServer）是一个独立的高权限特权进程。AppKit / SwiftUI 中的 `NSVisualEffectView` 和 `.glassEffect()` 本质上只是向系统合成器提交了一块“材质图层元数据（Material Layer Metadata）”。真正的背景像素抓取、模糊卷积、色差折射与光泽反射，全都在 WindowServer 的 GPU 阶段完成。
- **合成结果不可直接读取**：
  系统合成器负责把背景内容与材质效果合成到最终画面，但普通材质 API 不向应用暴露一个可直接读取“当前玻璃背后最终像素颜色”的接口。
- **隐私与安全保护边界**：
  苹果之所以严格单向隔离，是为了杜绝侧信道攻击。如果透明/磨砂窗口能得知底层像素的颜色或亮度，任何普通恶意软件都可以通过在屏幕上放置隐形透明窗口，逆向分析用户正在浏览的网页内容、银行账单或敏感密码。

### 2.2 系统级 `colorScheme` 与 `NSAppearance` 的局限
- SwiftUI 的 `@Environment(\.colorScheme)` 以及 AppKit 的 `NSAppearance` 仅代表当前 macOS **全局系统外观**（系统是处于深色模式还是浅色模式）；
- 它完全不感知窗口当前具体摆放在哪一张壁纸、或者哪一个特定应用的窗口之上；
- 如果全局系统是浅色模式，但用户当前正在一个黑色的 Terminal 窗口上方使用 Type4Me，系统的 `colorScheme` 依然是 `.light`，导致如果盲从系统外观，界面会绘制黑色文字在黑色终端上，彻底不可读。

## 3. 基于屏幕像素采样的「自适应」设计方案

为了真正达成“根据底层真实像素明暗动态反色”，团队设计并实现了基于 Quartz 屏幕采样的技术原型（`BackgroundLuminanceDetector`）。

### 3.1 架构与技术实现
1. **窗口底层区域裁剪（Quartz Window Coordinate Mapping）**：
   通过 `NSWindow.frame` 获取浮动面板在 AppKit 坐标系（左下角原点）下的物理外框，映射转换为 Quartz 屏幕坐标系（左上角原点）。
2. **底层像素抓取（`CGWindowListCreateImage`）**：
   使用 `.optionOnScreenBelowWindow` 与当前面板的 `windowID`，让系统 WindowServer 抓取严格位于浮动条正下方的局部屏幕矩形像素（排除了浮动条自身的干扰）。
3. **硬件级感知亮度计算（Perceived Luminance Calculation）**：
   将截取到的图像通过硬件加速绘制到一个 1×1 像素的 CoreGraphics 8-bit RGBA 位图上下文（利用双线性重采样自动计算区域平均色彩）：
   $$\text{Luminance} = 0.2126 \times R + 0.7152 \times G + 0.0722 \times B$$
   当 $\text{Luminance} \ge 0.45$ 时判定为浅色背景，触发 `.light` 主题；反之判定为深色背景，触发 `.dark` 主题。
4. **平滑防抖过渡**：
   在浮动条出现、位置尺寸变更或录音阶段以低频平滑采样，通过 SwiftUI `.spring(response: 0.3, dampingFraction: 0.85)` 平滑过渡文字颜色与图标反差。

### 3.2 该方案的优势
- **真正做到像素级智能**：无论底层是浅色壁纸、黑色终端还是红绿相间的图表，都能计算出最准确的加权平均明暗度，实现文字反差色的精准翻转；
- **纯粹的无底垫玻璃**：在深浅切换正确的前提下，玻璃背板完全不需要额外垫一层 0.22 浓度的黑底，玻璃的折射极其清透。

## 4. 为什么最终彻底废弃该方案？（代价与权衡）

在技术原型验证完成后，经综合评估，**该方案属于典型的“代价极高、体验极差的过度工程”**，决定彻底撤回并删除所有相关代码。核心原因如下：

### 4.1 致命的权限打扰与用户信任崩塌（Screen Recording / TCC）
- **引入额外屏幕捕获权限**：
  读取其他应用窗口的屏幕内容会进入 macOS 的屏幕捕获/TCC 权限边界；对于本方案而言，这意味着为了判断背景明暗而新增用户可见的 Screen Recording / Screen & System Audio Recording 类授权，权限成本远高于纯视觉增强本身。
- **极度糟糕的用户心理预期**：
  Type4Me 是一个注重隐私、轻巧克制的语音输入工具。当用户只是打开设置或开始录音，系统却突然弹窗提示：*“Type4Me 想要录制此电脑的屏幕”*，这会给用户带来极大的被监控恐惧与安全疑虑；
- **权限解释成本不可承受**：
  没有任何普通用户能理解“我录屏只是为了看一眼背景亮不亮来调文字颜色”。这种解释苍白无力，会直接导致用户流失与卸载。

### 4.2 App Store 审核与隐私说明成本
- App Store 对敏感权限的用途、必要性和用户说明有明确要求；
- 对语音输入工具而言，仅为自动选择文字反差色而新增 Screen Recording 权限，会增加用途解释、隐私披露和审核沟通成本。是否触发额外问询或影响审核结果取决于具体实现与提交材料，因此这里将其视为**不必要的审核不确定性**，而不是确定的拒审结论。

### 4.3 性能与电池成本
- 屏幕采样会增加额外的捕获、像素处理与调度开销；具体成本取决于所用 API、采样区域、频率和系统实现；
- 如果在录音期间持续或高频采样，即使只为计算平均亮度，也会产生本可避免的 CPU/GPU/内存与能耗成本。该功能收益不足以证明引入这些持续开销是合理的。

## 5. 最终设计结论与规范

Type4Me 在这一视觉功能上坚持**“不新增与核心输入能力无关的敏感权限、追求轻巧克制、保持工程纯粹”**的原则：

1. **彻底废除屏幕抓取与「自适应」模式**：
   移除所有 `CGWindowListCreateImage` 及相关检测代码，不向用户申请任何屏幕录制权限。
2. **固化两档纯净且直观的主题模式**：
   - **暗色（Dark，默认）**：
     针对复杂桌面壁纸和浅色窗口，采用经过充分调优的 Dock 级方案——原生玻璃 + `TF.glassDarkContrastFloor`（0.52 黑色底垫）+ 银白金属光泽文字（`Color.white.opacity(0.70)`）。即使覆盖在纯白网页上，依然能保持绝佳的文字可读性与高级感；
   - **明亮（Light）**：
     采用高透光浅色玻璃 + 高对比度深黑文字（`TF.floatingTextLight`），专为偏好明亮素雅界面的用户提供。
3. **由用户做主**：
   用户只需在「设置 → 外观设置」中根据自己的桌面风格二选一，交互语义清晰、确定、零副作用。
