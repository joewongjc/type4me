## 1. 背景与问题

### 1.1 PR #269 的初衷与演进
在 PR #269 之前，Type4Me 采用“录音开始时记录前台应用，并在转录结束后激活并回写该应用”的设计（#194 / #252）。为了满足 Issue #266 提出的“录音过程中查阅材料，录音结束时才选定输入框”的需求，PR #269 在「通用设置 → 录音设置」中增加了「手动录音写入目标」选项：
1. **录音开始时的应用**（默认）：录音结束后强制激活录音开始时的 App。
2. **录音结束时的输入框**：试图在停止录音瞬间通过 Accessibility (AX) 锁定当时聚焦的可编辑输入框，并在转录与 AI 处理期间持续监控焦点连续性。

### 1.2 Issue #291 暴露的系统性缺陷
在 Issue #291 中，用户在 **super.engineering**（一款基于 Rust + Metal 原生渲染、不包含 WebKit/Chromium/Electron 运行时的现代化 AI 编程环境）中使用 Type4Me：
- 在初始版本中，文字实际上已经通过 `Cmd+V` 正确进入了 super.engineering 的编辑器，但 Type4Me 的事后注入检测逻辑通过 AX 检查时判定为“未找到焦点”，从而误判为失败，强行将文本留在了剪贴板并弹出警示；
- 随后版本为了防止误写而进一步收紧目标验证条件后，super.engineering 因 AX 树仅暴露 `AXWindow` 且无法证明其内部私有编辑器的可编辑性，直接在前置验证阶段失败，导致连 `Cmd+V` 都不再尝试发送，彻底退化为剪贴板。

### 1.3 根因剖析：过度依赖 Accessibility 判定 first-responder
Apple 官方 API 规范中：
- `frontmostApplication` 的权威定义即为“当前接收键盘事件的应用（the application that is currently receiving keyboard events）”；
- 而 Accessibility API 明确允许应用不完全实现 AX 规范（返回 `kAXErrorNotImplemented`），且 `kAXFocusedUIElement` 仅为推荐属性。

在现代 macOS 软件生态中，存在大量使用自定义渲染引擎的应用（Rust + Metal、Flutter、Qt、Sublime/Zed、各类游戏引擎及终极端模拟器）。试图通过 AX 树在系统外层“证明”一个应用是否具有可编辑输入框，是一场永远无法穷尽兼容矩阵的追逐：
- **为了实现精确目标确认**：代码引入了全局输入监控 Epoch、Event Tap 拦截、Fn 释放尾部过滤、AXObserver 焦点变更监听、微信等不透明编辑器的启发式窗口探测；
- **为了实现注入结果验证**：代码引入了粘贴前后的 AX 快照比对，并强行用 AX 判定覆盖用户的剪贴板偏好；
- **代价与收益极度失衡**：仅为了支撑一个可选的回写偏好，引入了超过 1400 行极端脆弱的防御代码，不仅未彻底解决问题，反而破坏了正常应用的使用体验。

## 2. 核心产品决策：向系统输入法模型收敛

### 2.1 重新定义输入语义
Type4Me 是一款系统级语音输入工具，其用户心智模型应当等同于**键盘**和**系统原生输入法**，而非异步后台任务投递系统。

在普通手动交互式输入场景中：
> **永远不恢复/切换应用，也不在 Accessibility 中试图锁定特定的输入控件。语音处理完成后，直接向当前正在接收键盘事件的前台应用派发一次标准粘贴（`Cmd+V`）。文字落到具体哪个控件，完全由目标应用的原生 first-responder 路由机制自行决定。**

### 2.2 彻底废弃写入目标配置项
- **废弃设置**：从「通用设置 → 录音设置」中移除「手动录音写入目标」（`InjectionTargetPreference`），不再要求用户在“开始时的应用”与“结束时的输入框”之间做抉择。
- **单一心智**：用户当前正在看哪里、光标停留在哪里，文字就输入到哪里。

### 2.3 双轨制设计：交互式输入 vs 自动化任务

Type4Me 内部确立两条边界清晰、互不干扰的注入管线：

| 维度 | 交互式输入 (Interactive Input) | 自动化任务 (Automation / Headless) |
| --- | --- | --- |
| **触发场景** | 全局录音快捷键、菜单栏控制中心启动、手动输入窗口 | URL Scheme（`type4me://record`）、CLI 脚本、外部自动化 |
| **目标选择机制** | 完成时当前前台活跃应用（Current Keyboard Focus） | 启动时捕获的目标应用（Pinned Target Application） |
| **应用切换行为** | 绝对不激活、不切换应用 | 输出前重新激活 Pinned Target 并校验 PID |
| **Accessibility 角色** | 仅用于事后上下文感知与 Telemetry，不阻塞注入 | 辅助确认目标应用窗口状态 |
| **剪贴板策略** | 严格遵循用户的 `ClipboardOutputPolicy` | 严格遵循用户的 `ClipboardOutputPolicy` |

*注：改口（Voice Revise）功能因其核心语义为“替换当前选中的特定文本”，继续保留其专有的 Accessibility 选区定位与替换管道，不混入普通文本回写流程。*

## 3. 详细交互与行为规范

### 3.1 交互式输入的主流程
1. **开始录音**：用户在任意应用中按下录音快捷键，Floating Bar 展现录音状态。Type4Me 的 Floating Bar 本身即为 `nonactivatingPanel`，不会抢占目标应用的键盘焦点。
2. **停止录音**：用户松开快捷键或再次按下停止。系统立即进入转录与润色处理中状态，期间用户可以自由切换输入框或应用。
3. **完成输出**：
   - 检查当前前台应用（`NSWorkspace.shared.frontmostApplication`）；
   - 若前台应用为 Type4Me 自身（例如用户在此期间打开了 Type4Me 设置页或关于窗口），视为无外部输入目标，直接将结果写入系统剪贴板，浮层提示“已复制到剪贴板”；
   - 若前台应用为外部应用，将文字写入临时剪贴板并向其发送 `Cmd+V` 事件，完成一次即时粘贴派发；
   - 粘贴派发后，依据用户配置的 `ClipboardOutputPolicy`（如“仅取消时保留”或“从不复制”）按既有延时策略恢复原剪贴板内容；
   - 记录历史条目与 IntelliSense 学习，将当前前台应用作为感知上下文。

### 3.2 派发结果与剪贴板解耦
- **派发即完成**：只要 `Cmd+V` 成功写入系统事件队列，注入即视为已派发（`pasteDispatched`），浮层提示“完成”或进入正常淡出流程。
- **不再做 AX 结果审判**：不再因为 AX 树未检测到文本变化或未发现文本控件而覆盖用户的剪贴板保留策略。
- **真正的兜底场景**：仅当无法获取有效前台应用、CGEvent 创建失败或前台应用明确为 Type4Me 自身时，才进入剪贴板兜底模式，并展示明确提示。

### 3.3 接受的产品 Trade-off
- **焦点转移跟随**：如果用户在“停止录音”到“生成结果”的短暂间隔内（通常为几百毫秒至一两秒），主动使用 `Cmd+Tab` 或鼠标切换到了另一个 App，文字将进入新的活跃 App。
- **共识评估**：此行为符合物理键盘与系统输入法的客观规律——在输入法完成组字转换时，文字理应落在转换完成那一刻活跃的光标处。相比旧方案在后台强行将屏幕拉回旧 App、或是因为判断失败而直接放弃粘贴，当前方案的行为预期最为清晰稳定。

## 4. 设置界面与用户引导变更

1. **设置项清理**：
   - 从「通用设置」面板中完全移除「手动录音写入目标」这一选择行；
   - 清理所有相关说明文字，避免用 AX 术语（如“不透明编辑器”、“精确控件”）打扰普通用户。
2. **多语言对应**：
   - 同步清理中英文本地化字典中相关的废弃键值。
